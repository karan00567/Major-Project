# ResearchGPT — Run Registry Database Schema

> **What this file is.** The complete specification for the PostgreSQL run registry: what it stores, why, the DDL, the SQLAlchemy 2.0 models, and the failure semantics that keep it from ever breaking a run.
>
> **Stack:** PostgreSQL + **plain SQLAlchemy 2.0** (no Flask, no Flask-SQLAlchemy). The registry lives in-process inside the existing FastAPI backend as `src/researchgpt/db/`.
>
> Tasks: `TASKLIST.md` Phase 6B (T-620–T-626). Created 2026-08-25.

---

## 1. Purpose and scope

The registry is a **catalogue of runs**, answering: *what did we ask, with what configuration, when, and which files came out?*

It also resolves a live inconsistency. `SESSION_CONTEXT.md §7.2` flags slides 3, 8 and 9 of the Review-1 deck as claiming **PostgreSQL** while every other document says Chroma + SQLite. That was logged as a slide error to correct. Building this makes the deck's claim true instead.

### Three rules that define the design

**1. The registry is best-effort and never blocks a run.**
The pipeline writes artefacts to `outputs/runs/<run_id>/` and continues even if Postgres is down, unreachable, or never installed. Every registry call is wrapped so a database failure logs a warning and returns. This is the same rule that governs `TraceLogger`, which never raises into its caller.

> A registry bug must not be able to kill a 30-minute run four days before submission.

**2. Files stay on disk. The database stores pointers and metadata.**
No file bytes in Postgres. `outputs/runs/<run_id>/` is already created by the CLI and already covered by `.gitignore`; the registry stores **relative** paths so the tree stays portable.

**3. It is a catalogue, not a log.**
`trace.jsonl` is the per-event log and remains the source of every figure in the report. The registry does **not** duplicate it — it stores one row per run, with the trace file listed as an artefact. Do not add a `run_events` table.

`run_id` format is the one the CLI already produces: `20260825T094301Z-6c29fed3`.

## 3. Table: `runs`

One table. The artefact list is a JSONB array rather than a child table, so a run is a single row and a single read.

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `id` | `uuid` | PK, default `gen_random_uuid()` | surrogate key |
| `run_id` | `text` | UNIQUE NOT NULL | the CLI's run identifier |
| `research_question` | `text` | NOT NULL | the prompt given |
| `config` | `jsonb` | NOT NULL, default `'{}'` | full `RunConfig` snapshot |
| `status` | `text` | NOT NULL, CHECK | `pending` / `running` / `completed` / `failed` |
| `artefacts` | `jsonb` | NOT NULL, default `'[]'` | array of file descriptors, §4 |
| `metrics` | `jsonb` | NOT NULL, default `'{}'` | §5 |
| `error` | `text` | NULL | failure message when `status='failed'` |
| `created_at` | `timestamptz` | NOT NULL, default `now()` | |
| `completed_at` | `timestamptz` | NULL | set on terminal status |

`status` uses `text` + a CHECK constraint rather than a Postgres `ENUM` deliberately: adding a status later is a one-line constraint change instead of an `ALTER TYPE` migration.

---

## 4. `artefacts` — JSONB array element shape

```json
{
  "kind": "review_md",
  "filename": "review.md",
  "path": "outputs/runs/20260825T094301Z-6c29fed3/review.md",
  "bytes": 18432,
  "sha256": "3f7a…",
  "created_at": "2026-08-25T09:43:12Z"
}
```

`kind` is one of: `review_md`, `insights_csv`, `refs_bib`, `trace_jsonl`, `config_yaml`.

**Why `sha256` earns its two lines:** `make reproduce` (T-810) can then prove an artefact was generated by the recorded run and not hand-edited afterwards. For a project graded on not fabricating things, being able to demonstrate that is worth having.

---

## 5. `metrics` — JSONB object shape

Populated on completion, read from `trace.jsonl`:

```json
{
  "paper_count": 58,
  "claims_verified": 214,
  "claims_dropped": 14,
  "grounding_score": 0.87,
  "iterations": 2,
  "llm_requests": 71,
  "cache_hits": 0,
  "wall_seconds": 1840
}
```

`claims_dropped` is the field that matters — `PROJECT_PLAN.md §9.3` calls it *"the real measure of what the architecture buys."* Having it queryable across runs makes the ablation tables a SQL query instead of a manual tally.

## 6. DDL

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;   -- for gen_random_uuid()

CREATE TABLE runs (
    id                uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
    run_id            text        NOT NULL UNIQUE,
    research_question text        NOT NULL,
    config            jsonb       NOT NULL DEFAULT '{}'::jsonb,
    status            text        NOT NULL DEFAULT 'pending'
                                  CHECK (status IN ('pending','running','completed','failed')),
    artefacts         jsonb       NOT NULL DEFAULT '[]'::jsonb,
    metrics           jsonb       NOT NULL DEFAULT '{}'::jsonb,
    error             text,
    created_at        timestamptz NOT NULL DEFAULT now(),
    completed_at      timestamptz
);

CREATE INDEX ix_runs_created_at ON runs (created_at DESC);
CREATE INDEX ix_runs_status     ON runs (status);
CREATE INDEX ix_runs_artefacts  ON runs USING GIN (artefacts jsonb_path_ops);
CREATE INDEX ix_runs_metrics    ON runs USING GIN (metrics   jsonb_path_ops);
```

`ix_runs_created_at DESC` is the one that is actually hit — the Vue run-list is "most recent first". The GIN indexes are cheap insurance for querying inside `metrics` when building ablation tables.

## 7. SQLAlchemy 2.0 model

```python
from datetime import datetime
from typing import Any, Optional
import uuid

from sqlalchemy import CheckConstraint, DateTime, Index, String, Text, func
from sqlalchemy.dialects.postgresql import JSONB, UUID
from sqlalchemy.ext.mutable import MutableList, MutableDict
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column


class Base(DeclarativeBase):
    pass


class Run(Base):
    __tablename__ = "runs"

    id: Mapped[uuid.UUID] = mapped_column(
        UUID(as_uuid=True), primary_key=True, default=uuid.uuid4
    )
    run_id: Mapped[str] = mapped_column(String(64), unique=True, nullable=False)
    research_question: Mapped[str] = mapped_column(Text, nullable=False)

    config: Mapped[dict[str, Any]] = mapped_column(
        MutableDict.as_mutable(JSONB), nullable=False, default=dict
    )
    status: Mapped[str] = mapped_column(String(16), nullable=False, default="pending")
    artefacts: Mapped[list[dict[str, Any]]] = mapped_column(
        MutableList.as_mutable(JSONB), nullable=False, default=list
    )
    metrics: Mapped[dict[str, Any]] = mapped_column(
        MutableDict.as_mutable(JSONB), nullable=False, default=dict
    )
    error: Mapped[Optional[str]] = mapped_column(Text, nullable=True)

    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now(), nullable=False
    )
    completed_at: Mapped[Optional[datetime]] = mapped_column(
        DateTime(timezone=True), nullable=True
    )

    __table_args__ = (
        CheckConstraint(
            "status IN ('pending','running','completed','failed')",
            name="ck_runs_status",
        ),
        Index("ix_runs_created_at", created_at.desc()),
        Index("ix_runs_artefacts", artefacts, postgresql_using="gin"),
    )
```

### ⚠️ The one gotcha that will bite

`MutableList.as_mutable(JSONB)` and `MutableDict.as_mutable(JSONB)` are **not optional**.

With a plain `JSONB` column, SQLAlchemy tracks changes by *identity*, not by content. So this **silently does nothing**:

```python
run.artefacts.append({...})   # in-place mutation
session.commit()              # no UPDATE is emitted — the row is unchanged
```

The row is never marked dirty and the artefact vanishes with no error. Without the `Mutable*` wrappers the only safe pattern is whole-list reassignment (`run.artefacts = run.artefacts + [new]`). Use the wrappers and append normally.

## 8. Connection and configuration

```
DATABASE_URL=postgresql+psycopg://researchgpt:<password>@localhost:5432/researchgpt
```

Goes in `.env` (already gitignored) and `.env.example` with an empty value.

```python
engine = create_engine(
    os.environ["DATABASE_URL"],
    pool_pre_ping=True,     # survives a Postgres restart between runs
    pool_size=5,
    future=True,
)
```

`pool_pre_ping=True` matters on a development laptop where Postgres gets restarted or suspended; without it the first query after a resume fails on a stale connection.

**Dependencies** — add as a `db` extra in `pyproject.toml`, so the project still installs without Postgres:

```toml
db = ["sqlalchemy>=2.0", "psycopg[binary]>=3.1"]
```

**Migrations:** use `Base.metadata.create_all(engine)` at startup. Alembic is correct engineering and wrong for a 13-day timeline with one table and no production data. If the schema changes, drop and recreate — the registry is derived data, and every run is reconstructible from `outputs/runs/`.

## 9. Failure semantics

Every registry write goes through one wrapper:

```python
def _safe(fn, *args, **kwargs):
    """Registry writes are best-effort. A DB failure must never break a run."""
    try:
        return fn(*args, **kwargs)
    except Exception as exc:            # deliberately broad
        logger.warning("run registry unavailable: %s", exc)
        return None
```

| Condition | Behaviour |
|---|---|
| Postgres not installed / `DATABASE_URL` unset | Registry disabled. Pipeline runs normally. `GET /api/runs` falls back to a filesystem scan. |
| Postgres down mid-run | Warning logged, run completes, artefacts written to disk. Row may be left in `running`. |
| Row stuck in `running` | Cosmetic. A reconcile pass can mark rows `failed` whose `run_dir` has no `review.md`. |

**Verification (T-626): stop the Postgres service mid-run and confirm the run still completes with all artefacts on disk.** If that test does not pass, the non-blocking rule is not implemented, whatever the code looks like.

## 10. Queries the application needs

```sql
-- Vue run list (GET /api/runs)
SELECT run_id, research_question, status, created_at,
       jsonb_array_length(artefacts) AS artefact_count,
       metrics->>'claims_dropped'    AS claims_dropped
FROM runs ORDER BY created_at DESC LIMIT 50;

-- One run with its artefacts
SELECT * FROM runs WHERE run_id = :run_id;

-- Ablation table straight from the registry
SELECT config->'llm'->>'model'          AS model,
       config->'review'->>'max_papers'  AS max_papers,
       AVG((metrics->>'grounding_score')::float) AS grounding,
       AVG((metrics->>'claims_dropped')::int)    AS dropped
FROM runs WHERE status = 'completed'
GROUP BY 1, 2;
```

That last query is the payoff: `PROJECT_PLAN.md §9.4`'s ablation table becomes a query over recorded runs rather than a hand-assembled tally.

## 11. What this deliberately does not do

| Not included | Why |
|---|---|
| A `run_events` table | `trace.jsonl` is the log. §1 rule 3. |
| Storing file contents as `bytea` | Files stay on disk. §1 rule 2. |
| `pgvector` / embeddings in Postgres | Chroma owns vectors (`PROJECT_PLAN.md §2.2`). Moving them is out of scope and was already cut. |
| Paper metadata | SQLite `metadata_db` (T-203) owns that. Two stores, distinct jobs. |
| Alembic migrations | §8. |
| User accounts / multi-tenancy | Single-user project. |

## 12. Tables: `paper_scores` and `artefact_scores` — human judgement (T-612)

A reviewer opens a finished run, sees the papers the Extractor actually read and the review it produced, and scores each **1 (worst) to 5 (best)**. Two tables, because they answer different questions — *was the retrieval any good?* and *was the writing any good?* — and the automated metrics cannot currently tell those apart. Averaging them into one number would destroy the distinction the tables exist to record.

### The rule this feature had to reconcile

§9 says a database call must never raise into its caller, and §1 rule 3 says this is a catalogue, not a log. Both still hold, because **the score is appended to the run's `trace.jsonl` first and mirrored here second** — exactly how T-609's overrides already work.

* The trace is the record and keeps the **history** of a changed mind.
* These tables are the queryable **mirror** and hold one current row per `(run_id, target, reviewer)`.
* A Postgres outage costs the mirror and never the score. The API reports `persisted: "trace"` rather than `"trace+db"`, so the UI can say so honestly instead of claiming a write that did not happen.

That is §1 rule 3 applied, not bent: the log stays in the log, and the index stays an index.

### DDL

```sql
CREATE TABLE paper_scores (
    id         UUID PRIMARY KEY,
    run_id     VARCHAR(64) NOT NULL,
    paper_id   VARCHAR(64) NOT NULL,
    doi        TEXT,                       -- nullable, deliberately
    title      TEXT        NOT NULL,       -- snapshot of what was judged
    score      SMALLINT    NOT NULL,
    note       TEXT,
    reviewer   VARCHAR(64) NOT NULL DEFAULT 'human',
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT ck_paper_scores_range CHECK (score BETWEEN 1 AND 5),
    CONSTRAINT uq_paper_scores_run_paper_reviewer UNIQUE (run_id, paper_id, reviewer)
);
CREATE INDEX ix_paper_scores_run_id ON paper_scores (run_id);
CREATE INDEX ix_paper_scores_doi    ON paper_scores (doi);

CREATE TABLE artefact_scores (
    id         UUID PRIMARY KEY,
    run_id     VARCHAR(64) NOT NULL,
    artefact   VARCHAR(64) NOT NULL DEFAULT 'review.md',
    score      SMALLINT    NOT NULL,
    note       TEXT,
    reviewer   VARCHAR(64) NOT NULL DEFAULT 'human',
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT ck_artefact_scores_range CHECK (score BETWEEN 1 AND 5),
    CONSTRAINT uq_artefact_scores_run_artefact_reviewer UNIQUE (run_id, artefact, reviewer)
);
CREATE INDEX ix_artefact_scores_run_id ON artefact_scores (run_id);
```

### Three decisions worth knowing

**`run_id` carries no foreign key to `runs`.** The registry is best-effort (§9), so a run whose artefacts are on disk may never have been registered — it only takes Postgres being down while the pipeline ran. An FK would then reject a human's score for a run that demonstrably exists, inverting the rule: the index would refuse data *because the index is incomplete*.

**`paper_id` is the key and `doi` is nullable.** Roughly one OpenAlex record in five has no DOI. Measured on a real run: `W3167518830`, titled *"JBI evidence synthesis"*, has none at all — and a sheet keyed on DOI would silently drop exactly those papers. `doi` is carried for citation and for the reviewer's `doi.org` link, not as identity.

**`title` is denormalised into the row, and §11 still stands.** Paper metadata belongs to SQLite `metadata_db`; this is not a metadata store. It is a **snapshot of the title the reviewer actually saw when they scored**, which must not change when the corpus is re-fetched. Evidence of what was judged, not a copy of the catalogue.

### Range validation lives in two places

`CHECK (score BETWEEN 1 AND 5)` duplicates the Pydantic bound in `api/schemas.py`. That is intentional: validation at one layer only is validation that can be walked around, and a score written by `psql` or by a later analysis script must still be in range.

### What this deliberately does not do

| Not included | Why |
|---|---|
| Feed scores back into retrieval or ranking | Collection only. The optimizer is a later task and gets that name when it exists. |
| Identity / multi-rater support beyond `reviewer` | Single-user project. The column exists so a second rater needs no schema change — but §8 has no Alembic, so adding one means drop-and-recreate. |
| Scoring papers outside the extracted corpus | A run retrieves thousands and extracts ten. Nobody hand-scores thousands, and there is no human judgement to record about a paper nobody read. |
